## 二、做得好的地方

### 2.1 架构设计 — 分层清晰

- **Profile 分级巡检**（`checks.py:run_all`）：5m/10m/hourly/daily 四档频率，高频轻量、低频全量，对 API Server 压力有合理控制。5m 跳过 metrics-server 查询的设计很务实。
- **模型驱动输出**：`models.py` 定义了 `Status` / `CheckResult` / `Report` 三个核心数据类，报告/通知/指标层全部消费模型，不直接接触检查内部实现。
- **模块拆分合理**：`cli.py`(入口) → `checks.py`(规则) → `report.py`(输出) → `metrics.py`(Pushgateway) → `notify.py`(飞书)，职责清晰。

### 2.2 代码质量 — 稳健、防御性强

- **每个检查函数都捕获所有异常**（`checks.py`），返回 `WARN` 而非崩溃，单个检查失败不影响整体。这是运维工具的最佳实践。
- **类型标注完整**：`from __future__ import annotations` + 标准类型标注，`dataclass` 使用得当。
- **`common.py` 被 mcp_server 复用**（而非重复实现），`parse_quantity`、`pod_issue` 等核心逻辑集中管理。
- **`state_store.py` 原子写入**：`tmp + os.replace` 避免 JSON 文件写坏。这个细节做得很好。

### 2.3 可观测链 — 生产级完整

- **Pushgateway 模式**契合 CronJob 短生命周期场景，设计选择正确。
- **Prometheus 规则**增加了 `K8sInspectorStale` 抑制规则，防止 Pushgateway 旧值误报。
- **Alertmanager → 飞书桥接**（`alertmanager_bridge.py`）做到了聚合去重、自动拉群、自动改名 `[已解决]`，远超简单 webhook。
- **Grafana 大盘 JSON** 已提供。

### 2.4 部署工程化

- **Kustomize 一键部署**：RBAC / CronJobs / Pushgateway / Alertmanager / Bridge 全套。
- **存储分层**：latest 覆盖 + archive 归档 + cleanup CronJob 清理。
- **Dockerfile** 精简有效。

## 三、不足之处

### 3.1 缺少 etcd 健康检查

README 中列出了 etcd 巡检维度（集群健康、磁盘使用率、leader 切换），但代码中 `check_control_plane()` 只检查了 apiserver /healthz 和控制平面组件 Pod 状态。**这是最显眼的遗漏**。虽然部分集群 etcd 是托管服务，但自建 etcd 场景下这个检查很关键。

### 3.2 Pod 检查重复调用 K8s API

`check_pods()` 中，对每个 Pod 调用了两次 `_pod_issue_from_obj()`（先 `restart_threshold=0` 判断 bad，再 `restart_threshold=N` 判断 restart_heavy），其中第二次对 bad Pod 也被 `continue` 跳过了，逻辑正确但冗余。可以在一次遍历中同时完成两种判断。

### 3.3 缺少集成测试

95 个测试全部是单元测试（Mock K8s API），没有集成测试验证：
- 真实的 K8s API 交互链路
- Report 生成 → Pushgateway 推动的端到端流程
- Alertmanager Bridge 的实际 HTTP 处理

### 3.4 MCP Server 与主模块部分代码重复

`mcp_server.py` 中的 `Thresholds` / `InspectorConfig` / `get_node_metrics()` / `_pod_issue_from_obj()` 与主模块的 `config.py` / `checks.py` / `kube.py` 存在重复实现（虽然 CLAUDE.md 声明是"有意为之"以独立部署，但这是两难问题，实际维护成本是存在的）。

### 3.5 缺少并发控制

`checks.py:run_all()` 中的检查函数是**串行执行**的。在 full profile 下，6 个检查串行耗时可能较长。各检查之间无依赖关系（都只读 K8s API），完全可以并发执行。

### 3.6 报告缺少历史对比能力

每次巡检结果独立输出，没有机制对比"这一次 vs 上一次"的变化。例如"上次有 NotReady 节点 2 个，这次变为 1 个"在报告中无法体现。

### 3.7 HTML 报告功能偏弱

`report.py:write_html()` 只渲染了 CheckResult 的 name/status/summary/duration_ms，没有展示 `data` 字段的详细内容（如具体哪些节点 NotReady、哪些 Pod 异常），人工排查时仍需查看 JSON。

## 四、改进建议

### 4.1 高优先级（建议近期完成）

| 序号 | 改进项 | 建议方案 | 预估工作量 |
|------|--------|----------|-----------|
| 1 | 补充 etcd 健康检查 | 新增 `check_etcd()`，检查 etcd 成员健康/磁盘/leader 切换 | 2-3h |
| 2 | Pod 检查去重调用 | 合并 `_pod_issue_from_obj` 两次调用为一次返回 issue 和 restart_issue | 0.5h |
| 3 | 并发执行检查 | 在 `run_all()` 中使用 `concurrent.futures.ThreadPoolExecutor` 并行执行 | 1h |
| 4 | HTML 报告增强 | 在 HTML 中渲染 data 字段的关键结构（not_ready 列表、bad pods 等） | 2h |

### 4.2 中优先级

| 序号 | 改进项 | 建议方案 | 预估工作量 |
|------|--------|----------|-----------|
| 5 | 添加集成测试 | 使用 `kind` 创建临时集群跑真实检查 | 4-6h |
| 6 | 历史对比 | 读取上一次 report.json，在报告中 diff 变化项 | 3-4h |
| 7 | CLI 增加 `--dry-run` | 只执行检查不写文件/不推送 | 0.5h |
| 8 | 增加 Pod disrupt budget 检查 | 检查是否有 PDB 配置不当导致无法驱逐 | 1-2h |

### 4.3 低优先级

| 序号 | 改进项 | 建议方案 |
|------|--------|----------|
| 9 | 支持钉钉/企业微信通知 | 扩展 `notify.py` 的通道适配 |
| 10 | MCP Server 增加更多工具 | 如 `get_pod_logs`、`exec_into_pod` 等 |
| 11 | 支持多集群并发巡检 | `--kubeconfig` 支持多个文件或目录 |
