# 第一批整改实施记录：固定责任群通知

日期：2026-10-02。用户已确认告警路由与建群整改方向。本批完成固定责任群通知、来源保留与交付基础验证，是 [建群专项方案](C:/Users/23033/Desktop/Cluster-Stability-Inspector/审计/07-告警路由与建群策略-2026-10-02.md) 的第一阶段实现。全项目整改与事件协作流程尚未全部完成。

## 已完成的行为

1. **停止按通知分组自动建群。** Bridge 不再将 groupKey 映射到群，不调用 create_chat、rename_chat，也不自动邀请成员。`FEISHU_CHAT_POLICY` / `--chat-policy` 默认且目前仅支持 fixed；其他策略启动报错，不保留一条可意外开启旧自动建群的路径。
2. **保留两种发送方式。** webhook 向已有群发文本；app 向已有 chat_id 发卡片。app 不再要求被拉群成员 open_id，改为要求固定兜底群。
3. **增加责任路由。** JSON/YAML 文件按每条告警标签精确匹配、顺序选择第一条路由；缺少标签或未命中时发送兜底群。同目标群合并卡片，不同目的地只接收属于自己的告警条目。当前 owner_team 尚未统一输出，先支持已有 cluster/alertname/check 等标签。
4. **修正混合批次展示。** 每条展示来源信息；同时显示 firing 与 resolved，识别上游 truncatedAlerts。恢复通知明确只描述所列告警，不自动推断整个事件已结案。
5. **防止错误报告背景。** 仅同 cluster/profile、有效时间且在 profile 新鲜度窗口内的巡检快照可以附带；混合来源、责任路由和团队/namespace/service 范围的通知不附带整集群报告。profile 只能从内置集合选择，文件解析后路径必须留在报告根目录内。附带快照明确标注为辅助背景。
6. **确认实际交付。** webhook 检查 HTTP 与飞书业务响应，拒绝非零 code、无效 JSON、缺少成功码和其他未确认结果；兼容仅有 StatusCode=0 的旧响应。HTTP 接收服务在实际发送成功后才返回 200；交付失败返回 500。某一责任群失败仍尝试其他群。
7. **补充入口与生命周期基础修复。** 请求限制为 1 MiB，拒绝非法/重复 Content-Length 与不支持的 Transfer-Encoding；校验 Alertmanager payload。监听主机参数生效，SIGTERM/SIGINT 的 shutdown 在另一个线程执行，退出时关闭监听 socket。
8. **同步部署与说明。** 两份 Alertmanager 配置按 cluster 聚合；Deployment 改为固定群配置，移除旧空状态卷，增加进程健康探针和示例资源限制。README 与 AGENTS.md 更新到新行为。

新增模块 [alert_routing.py](C:/Users/23033/Desktop/Cluster-Stability-Inspector/k8s_inspector/alert_routing.py) 负责标准化与目的地路由；[Bridge](C:/Users/23033/Desktop/Cluster-Stability-Inspector/k8s_inspector/alertmanager_bridge.py) 负责接收与投递。飞书 SDK 管理群的方法仍可供以后事件升级使用，本批 Bridge 无调用路径。旧 JsonStateStore 保留为历史映射组件，本批 Bridge 不再使用。

## 配置与升级

app 模式需要预先建立责任群、将应用机器人加入群，并配置：

```bash
# FEISHU_APP_ID / FEISHU_APP_SECRET 通过环境变量提供
python -m k8s_inspector.alertmanager_bridge --mode app --feishu-chat-id oc_your_existing_chat --chat-policy fixed
```

部署 Secret 增加必需的 `fixed_chat_id`，见 [Secret 示例](C:/Users/23033/Desktop/Cluster-Stability-Inspector/deploy/secret-feishu.example.yaml)。CLI/环境提供的兜底群优先于路由文件中的 default_chat_id。可选路由见 [配置示例](C:/Users/23033/Desktop/Cluster-Stability-Inspector/deploy/feishu-routes.example.yaml)，该文件不是 Kubernetes 资源，不直接 kubectl apply。

旧自动拉群成员、群名模板、恢复后缀与状态路径环境变量不再控制通知；对应旧 CLI 参数已移除。缺少固定群时服务启动失败，避免悄悄回到自动建群或丢通知。

已有飞书群不会被本批程序修改。旧映射文件也不会被读取、迁移或改写。但旧 Deployment 使用 emptyDir，替换 Pod 会删除该临时卷；若需要留存映射，必须在替换旧 Pod 前导出 `/data/state/feishu_chats.json`，供后续人工登记。

详细参数、ConfigMap 挂载方法和升级步骤见 [README](C:/Users/23033/Desktop/Cluster-Stability-Inspector/README.md:241)。健康探针表示接收进程存活，不代表飞书链路已经成功投递。

## 已知边界与后续批次

- **尚无持久投递去重/队列。** 当前语义为收到后同步发送，再 ACK。HTTP/网络结果不明，或多群部分成功后整批重试，成功目的地可能重复收到消息。不能宣称恰好一次投递。
- **尚无业务事件状态机。** 当前 resolved 只展示上游状态，没有自动事件恢复、结案或重新开案动作；人工事件升级、负责人、成员集合与协作群绑定仍待实现。
- **尚未全面消除重复规则。** HasFail/CheckFail/PendingPVC 及跨 profile 的重复观察仍可能出现在聚合通知中。下一批需整理规则覆盖和主要来源，不能过宽抑制其他独立故障。
- **路由依赖可信标签。** 当前接收入口鉴权、来源规范化、完整资源身份、SDK 写操作幂等与限速仍待补强。生产接入前应继续完成既定入口和交付整改。
- **报告背景不是事件证据。** 阻断了可确认的错误身份、过期和跨责任范围附带，但报告原子发布、latest 恢复更新与完整 Finding 模型尚未完成。
- **既有检查与部署问题仍按总路线图整改。** 本批没有将全项目 F01–F36 标记为全部解决。

下一批优先完成可靠投递与告警去重，包括持久接收/投递记录、失败与不明结果处理、重试边界和规则覆盖梳理；之后实现人工事件升级。自动事件关联和自动建群继续保持未启用。
