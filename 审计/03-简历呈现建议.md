## 适合写在简历上的理由

1. **覆盖 SRE 核心技术栈**：Kubernetes SDK、Prometheus、Alertmanager、Pushgateway、Grafana、飞书 API
2. **工程化程度高**：不是一次性脚本，而是有配置管理、分级执行、多格式输出、部署清单的完整项目
3. **从 0 到 1 构建**：包含 CLI 工具 + MCP Server + Alertmanager Bridge 三个独立服务
4. **有 DevOps 链路的思考**：存储分层、退出码策略、Pushgateway 旧值抑制、并发限流

## 面试可能被追问的点（建议准备）

| 追问方向 | 准备要点 |
|----------|---------|
| 为什么不用 kube-prometheus-stack 自带的能力？ | 该项目解决的是"主动检查"而非"被动监控"，两者的告警触发条件不同。例如，巡检可以检查 PVC pending 状态，而 Prometheus 不容易对 "PVC phase" 做指标采集 |
| Pushgateway 旧值误报怎么处理？ | 通过 `K8sInspectorStale` 规则做新鲜度约束；last_run 超时则抑制 FAIL/WARN 告警 |
| 如果 K8s API Server 已经挂了，巡检怎么办？ | `INSPECTOR_EXIT_MODE=always0` + Prometheus 的 `absent()` 函数检测指标缺失来间接告警 |
| etcd 检查为什么没做？ | 如托管集群（EKS/GKE/TKE）etcd 不可见；自建集群可通过 exec into etcd pod 的方式补充 |
| MCP Server 的 API 限流怎么设计的？ | 三层：令牌桶 RPS 限速 + burst 容量 + in-flight 信号量，均支持环境变量配置 |
| check_pods 为什么遍历全部 Pod？ | 当前版本遍历全集群 Pod 做问题筛选；大规模集群可优化为先按 namespace label 过滤 |

## 与同类开源项目对比

| 项目 | 定位 | 本项目的差异化 |
|------|------|---------------|
| kube-bench | 安全合规扫描 | 本项目侧重健康状态 + 资源审计 |
| k8sgpt | LLM 驱动的 K8s 诊断 | 本项目 MCP Server 做了类似的事，但更轻量 |
| Popeye | K8s 集群扫描 | 本项目多了分级频率 + 飞书告警 + Prometheus 集成 |
| k9s | 交互式 TUI | 本项目是自动化 + 无人值守的设计 |

**核心差异**：本项目提供了从**巡检 → 指标 → 告警 → 通知**的完整闭环，而非单个扫描工具。
