## 执行方式

使用本机已有 uv 0.11.19，将独立 Python 安装到仓库 `.superpowers/tools/python-runtimes`，显式指定本地缓存并使用 `--no-bin --no-registry --no-config`。未修改系统 PATH 或 Windows 注册表。运行时来源为 uv 管理的 Astral python-build-standalone，参见 [uv 官方说明](https://docs.astral.sh/uv/guides/install-python/)。

实际下载并启动的解释器为 Windows x86_64 CPython **3.9.25、3.11.16、3.14.7**。它们只能提供本地 Windows 证据，不能替代准备中的 Linux CI 或固定 Python 镜像验收。

每个版本分别创建无系统 site-packages 的全新 venv，从公开 PyPI 安装 `requirements.txt`，记录安装前包清单、安装日志、`pip check` 与完整 freeze。后续用相应解释器实际构建 wheel，并在第二个全新 venv 中安装运行时依赖、验证安装位置；干净安装阶段不使用共享依赖 `.pth`。源码完整回归仍包含原有明确标记的离线 fixture，二者的证明范围保持区分。

运行校验器时清除 PYTHONPATH/PYTHONHOME/VIRTUAL_ENV 与额外 pip index/find-links 等环境配置，固定公开 PyPI。完整 release success 仍受 Docker 和真实环境验收约束；本地 CI 门槛由独立字段表示。

## 首次尝试与环境调整

深层计划临时目录中的 Python 3.11 干净安装失败，pip 报 `OSError: [Errno 2]`，路径指向 lark SDK 的长文件名。现有完整 SDK 的最长相对文件路径为 143 字符；深层 venv 使绝对路径超过 Windows 常见路径长度限制。结合失败路径长度和短路径重试结果，定位为本机长路径问题；传统 MAX_PATH 及长路径启用条件参见 [Microsoft 官方说明](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)。保留失败日志，3.9 的首次安装在获得结果前中止，3.14 未在该深层布局尝试；不把中止记录为版本不兼容。

随后改用专属短目录 `out/ra`，带明确 OWNER 标记；测量后的候选安装路径留在限制内。只改变本轮测试环境布局，不修改系统长路径设置、不修改依赖以掩盖环境问题，也不声称支持任意深度的 Windows 安装路径。

第一次短路径标准 pip 尝试在 SDK 批量生成字节码阶段中止，不算成功或版本不兼容。之后重新创建干净 venv，显式用 `pip install --no-compile`；安装前检查关闭用户 site-packages，3.14 的初始包清单只有 pip，实际验证了 dev extra 提供 setuptools/wheel，而非借用环境已有后端。三版本依赖安装和 `pip check` 均通过。

第一次独立 wheel 验证还发现作者编排脚本的错误：`PIP_NO_COMPILE=1` 在实际 pip 参数解析中得到 `compile=1`，仍开启编译，触发 180 秒安装超时。保留参数探针与旧尝试，改用已实测的 `PIP_COMPILE=0`，清除负向变量，使用全新 `w<version>` 安装目录和 `matrix-corrected` 日志重跑。此前部分运行不计入最终通过结果；项目代码与依赖未因此修改。

每次跳过的两项均为真实 Docker CLI/Bridge 入口 smoke；未执行容器测试。干净 wheel venv 的实际依赖安装、安装位置检查、`pip check`、不含 build/pytest 的断言，以及 kubernetes、PyYAML、prometheus-client、lark-oapi 四个运行时依赖的实际导入均通过。

独立安装包探针使用 `-I -B -X utf8`，工作目录位于源码导入路径之外。每个版本执行 CLI help/run help/cleanup help、Bridge help、bridge_admin help、expected_targets help、pip check、运行时隔离断言和依赖导入，共 **27/27** 项通过。只执行帮助和本地检查，未启动真实通知发送。3.11 的探针复用前核对 wheel SHA；其余版本使用各自 wheel 和全新安装环境。

三版本均通过 base/example/shadow 三种 Kustomize 渲染，组合后的 Prometheus/Alertmanager 配置检查，20 条巡检规则及 11 组时序用例、7 条 Bridge 规则及 2 组时序用例。工具版本和输出随证据归档。

3.9 的 7 条警告为 2 条 google-auth 对 Python3.9 EOL 的维护提示，以及 5 条 lark SDK/setuptools 的 pkg_resources 命名空间警告。保留实际兼容测试通过的事实与原 >=3.9 声明，主发布 Python3.11 计划不变；兼容性通过不等于上游仍提供完整维护，后续版本支持策略需单独决定。

3.14 的 1 条警告来自 lark 所带 protobuf 对 `datetime.datetime.utcfromtimestamp()` 的弃用提示。源码完整回归未失败；本轮不通过修改上游依赖或屏蔽警告改变证据。

SDK 冷导入在本机无字节码的环境中较慢，3.9/3.14 的独立导入分别记录为 204.83/280.91 秒。后续探针为该项保留 900 秒预算，其余项为 120 秒。这些数字只描述本次 Windows 测试，不能作为容器启动速度或生产 SLO。
