## 实施范围与取舍

规划先按“单集群部署、复用已有 Prometheus/Alertmanager、Bridge 单实例、MCP 可选”估算。这是为了让第一版改造能落地，不是限制项目以后扩展。真实集群规模、托管/自建、监控现状、飞书模式与留存要求尚未提供；先做不依赖这些答案的确定缺陷修复，扩展能力前再落实环境参数。

| 决策 | 推荐选择 | 何时调整 |
|---|---|---|
| 语言与任务运行方式 | 保留 Python + CLI + CronJob | 有实测性能或长期常驻采集需求才换运行模型 |
| 主告警通道 | 已有 Prometheus → Alertmanager → 固定责任群；webhook 发文本或 app 向已有 chat_id 发卡片 | 重大故障先人工升级到事件协作群，自动建群在事件关联与可靠交付达标后开放 |
| Bridge 状态 | 单实例、本地持久卷上的 SQLite/事务存储 + pending delivery | 多副本时改共享数据库，不用共享 NFS JSON/SQLite 冒充 HA |
| 高频报告 | 每次运行更新 latest，issue 历史按策略保存 | 多集群/长期留存再接对象存储 |
| 插件机制 | 简单 rule 注册表和 profile 配置 | 外部规则作者和版本协商需求真实出现后再做插件平台 |
| 主动探针 | 可选、明确权限与目标 | 需要证明 DNS/网络/业务可用性时启用 |
| AI/MCP | 只读可选入口，共用采集和规则语义 | 身份授权、数据治理及关键诊断正确后再增加能力 |
| etcd 检查 | 优先已有只读指标/端点 | 不因功能缺口默认给巡检 SA pods/exec 或 cluster-admin |

## S1：优先减少漏报、假恢复和通知丢失

**判定修复**：读取普通/init 容器与 Pod conditions，设置 Pending/unready grace period；对已结束 Job Pod 和历史 OOM 分类；PVC Lost 直接输出发现。先收集全部发现，再计算业务摘要，任何后续解析错误不降低已确认故障等级。

**运行保障**：统一 connect/read timeout，检查 deadline 和总 deadline；Deadline 必须通过到底层请求，不能只在 Python 线程外围超时后继续留下阻塞请求。重试预算属于运行预算的一部分。为 Job 加 activeDeadlineSeconds，与下一轮运行间隔协调。

**交付保障**：latest 始终更新，报告文件临时写入后 replace；sink 相互隔离，必需交付失败形成明确运行失败。飞书成功必须满足业务成功响应；对 app 写操作建立幂等与待发送状态。

**安全默认值**：TLS 校验打开，MCP 默认本地入口；Bridge 请求认证、payload 边界、profile enum 与路径 containment。修复 listen_host 与 shutdown 同线程死锁；探针检查进程是否可服务，readiness 不能盲目证明所有下游凭据有效。

**验收**：已确认故障仍在、采集失败可见、恢复需要有效证据、通知失败可重试；报告损坏/盘满/禁止访问不会令其他交付路径悄悄消失。

## S2：重构最关键的领域契约

建议结构是渐进迁移目标，不要求为每个函数建一层抽象：

```text
k8s_inspector/
  cli.py
  domain/
    models.py             # Run / CheckExecution / Finding / ResourceRef
    policy.py             # 严重度、维护窗口、汇总和兼容行为
  collection/
    kubernetes.py         # 认证、超时、分页、错误分类、客户端生命周期
    context.py            # 本次运行复用、采样时间、覆盖率
    prometheus.py         # 确实需要时间窗口的数据才接入
  rules/
    nodes.py
    pods.py
    storage.py
    control_plane.py
    workloads.py
    registry.py           # 小型注册表与 profile 定义
  runner.py
  outputs/
    reports.py
    metrics.py
  notifications/
    feishu.py
  bridge/
    http.py
    incidents.py
    store.py
    delivery.py
  mcp_server.py           # 入口适配器，逐步调用共享诊断能力
```

模型至少包含：

| 模型 | 必需字段/语义 |
|---|---|
| Run | schema_version、run_id、cluster_id、profile、开始/结束时间、config digest、execution summary、sink results |
| CheckExecution | rule_id、执行状态、耗时、采集来源、observed_at、coverage、错误种类、skip/unsupported 理由 |
| ResourceRef | kind、namespace、name、UID、container、owner/workload、node 等可选关联 |
| Finding | 稳定 rule_id、严重度、资源身份、reason、summary、结构化 evidence、时间窗口、建议、fingerprint |
| Incident | incident_id、correlation_key、episode、成员告警 fingerprint 与来源、first/last seen、last valid health、负责人、当前状态、chat_id、pending deliveries、外部操作状态 |

明确规定：

- 执行 `ERROR/PARTIAL` 时不能凭缺失发现产生健康结论。
- `UNSUPPORTED` 与临时错误不同，显示能力边界；必需能力缺失时整体运行不能伪装完整。
- `SKIPPED` 必须说明策略来源，例如 profile 或带期限的维护排除。
- aggregate status 为显示兼容字段，不能代替 Findings 和 execution status。
- evidence 具有采样时间；跨资源采集不保证事务一致性，但需披露时间差与缺失。
- severity、执行状态、当前/历史异常不混用一个从小到大的数值枚举。

**配置**：用 dataclass + 显式验证或已选择的类型模型即可；不为配置工具本身引入复杂框架。未知字段报错；有限数值、非负阈值、命名空间/selector/URL、期限与频率校验；文档化 CLI/env/file/default 优先级，输出脱敏有效配置。

**迁移**：先加入新字段和 adapter，保留 v1 summary/status；再把规则按领域迁入，最后让报告/metrics/Bridge 消费结构化 Finding。客户端共享逻辑与 SDK 专有对象在采集层结束，不把“每条规则都创建客户端”迁入新目录。

## S3：建立可靠告警闭环与可部署版本

**事件流**：接收已鉴权 webhook → 校验并标准化 → 事务记录 incident 变更与 pending delivery → 受控 worker 执行飞书操作 → 确认交付/记录错误 → 有界重试/人工处理。响应 2xx 表示可靠接收后的语义需要写清楚；若没有持久化接收能力，就必须以实际交付成功作为 ACK 的依据。

状态至少区分 `FIRING`、`UNKNOWN`、`RESOLVED`，发送状态独立。UNKNOWN 不改群名“已解决”。缺数据后的补采恢复、重开故障、Alertmanager duplicate、乱序和 Pod 替换必须有案例。外部 API 无 exactly-once 保证时承认 at-least-once，利用可用幂等参数与 reconciliation 降低重复。

**通知策略**：固定责任群承接常规告警，默认关闭自动建群；值班人员确认重大故障和协作需要后，按独立 incident_id/episode 创建或绑定事件群。Alertmanager groupKey、告警 fingerprint、业务 incident_id 分别建模；profile 不作为事件身份。app 发送方式与是否建群解耦，app 也可向已有群发卡片。事件关联与可靠交付完善后，再开放明确规则的自动升级。报告按告警对象和有效采样匹配，不能从任意 latest 抄一份故障摘要。详见 [告警路由与建群策略](C:/Users/23033/Desktop/Cluster-Stability-Inspector/审计/07-告警路由与建群策略-2026-10-02.md)。

**指标建议**：保留旧名作为短期兼容，增加运行和采集质量，而不是仅增加更多 issue count。

```text
k8s_inspector_run_success{cluster,profile}
k8s_inspector_run_duration_seconds{cluster,profile}
k8s_inspector_last_completed_run_timestamp_seconds{cluster,profile}
k8s_inspector_last_valid_observation_timestamp_seconds{cluster,rule}
k8s_inspector_check_execution_status{cluster,rule,status}
k8s_inspector_collection_coverage_ratio{cluster,source}
k8s_inspector_sink_success{cluster,profile,sink}
```

这些是待设计名称，并非已存在指标。expected cluster/profile/required rule 清单应来自独立配置或受监控的 inventory，不能仅由可能完全启动失败的 Inspector 自己 push。详细对象证据留在报告/事件记录；对 label 数量和故障文本设预算。

**PromQL 验证**：空数据、仅一档缺数据、旧 FAIL、FAIL→采集 ERROR、FAIL→有效 PASS、Pushgateway 丢数据、同 rule 多档执行、多集群同名节点、SKIP 与 FAIL 同时存在。规则单源生成 ConfigMap；使用 promtool unit test，而不仅 check syntax。

**部署拆分**：

```text
deploy/
  base/                    # inspector + 最小 RBAC + 参数化 CronJob
  components/bridge/       # 可选，含探针和状态卷
  overlays/demo/           # 演示监控栈，明确易失状态边界
  overlays/production/     # 复用现有监控、已有 storageClass/PVC、资源与权限
  examples/                # NFS、Secret 模板、手工集成片段
```

使用专用 namespace；PrometheusRule/ServiceMonitor 仅在已有相应 CRD 的环境 overlay 提供，原生 Prometheus 接入保留配置方式。检查 secret 前置条件，集中管理镜像、cluster_id、服务 URL、存储和 schedule/timeZone。cleanup/Bridge/monitoring 默认不挂巡检全集群 token。

**验收**：渲染产物无未知引用/占位符，真实存储可绑定；节点/API/文件存储/Pushgateway/Feishu/Bridge 分别故障时，运行结论和通知路径有明确行为；停止 Inspector 也能由独立监控发现。

## S4：有顺序地补足巡检能力

| 顺序 | 新能力 | 为什么优先 | 完成标准 |
|---|---|---|---|
| 1 | 工作负载可用性与 rollout | Pod 健康不能证明期望副本达标 | Deployment/STS/DS generation、desired/ready/available、滚动宽限期与 owner 关联 |
| 2 | Node pressure 与容量/requests | 已有 API 能提供较多证据 | 条件、maintenance、allocatable/usage 分开，基线与趋势来源明确 |
| 3 | PVC/PV/SC/CSI 与挂载失败 | 当前 Lost 漏报，Pending 误报明显 | WFFC/消费者/持续时间、关键事件、容量数据源与 unsupported 行为 |
| 4 | 控制面与 etcd | README 已过度承诺 | 托管/自建能力模型，readiness、授权指标和 HA/仲裁语义 |
| 5 | DNS/CNI 功能探测 | Running 不能证明网络功能 | 受控只读/探针策略、明确目标、超时、限频与结果证据 |
| 6 | 证书/版本/PDB/配额风险 | 增加提前发现能力 | 每项 source、threshold、误报策略和维护排除可验证 |
| 7 | 业务合成请求 | 最接近实际影响，但环境依赖最大 | 与用户指定业务目标/SLO 对应，不默认扫描任意服务 |

| 生命周期 | SIGTERM、连接读取超时、停止接收与在途交付 | 有期限子进程测试，避免测试挂死 |
| 构建/部署 | extras、生产 Python、镜像入口、Kustomize refs、RBAC/Secret/PVC | 包/镜像 smoke + render/lint + 测试集群 dry-run |
| 真实闭环 | 故障→有效发现→告警→消息→证实恢复→解决 | kind/测试集群和专用测试机器人，另行授权真实发送 |

测试增加要针对风险，不追求机械数量。所有关键未知/失败路径都有断言，禁用 `assert True` 类占位验证。CI 测试不得依赖生产 kubeconfig 或实际机器人凭据。

## 灰度、回滚与运营标准

1. 先在测试集群跑新版本，模拟 Pod 不 Ready、init CrashLoop、Lost/等待消费者 PVC、403、metrics 缺失、push 失败和 Bridge 重建。
2. 在目标集群以“只出报告、不发实际通知”的 shadow 模式与旧规则对比，使用独立输出目录和 Pushgateway job/grouping，避免覆盖旧数据。
3. 对比发现数量、对象级误报/漏报、采集成功率、API 请求数、运行 P95/最大耗时和报告大小。旧版不可靠，不以“新旧完全相同”作为目标；差异需要人工解释与证据。
4. 先放量一个 profile 或业务范围，再开启统一告警；短期双运行不要双发通知。历史 grouping 退出有显式删除/退役策略。
5. Bridge DB schema 与外部群映射有迁移/备份；回滚要验证旧程序能否读取新状态，不能只回退镜像就宣布可回滚。
6. 连续观察 7–14 天，至少完成一次报警和有效恢复演练，制定 runbook、owner 与配置变更流程。

建议验收指标：关键回归场景 100% 正确；运行超时可控且不会阻塞下一调度；正常采集覆盖率达配置目标；必需 sink 失败可见；同 incident 并发不重复建群；有效恢复不丢通知；日志无明文凭据。可用性百分比、误报预算、规模与耗时阈值应在真实环境基线后约定，不能凭代码评审编造已达成的 SLO。

**实施起点：S0 + 第一批补丁 1–4；有 app 模式生产使用时，补丁 5 与入口安全同步优先。**
